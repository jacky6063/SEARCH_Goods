# 購物客服架構調整任務紀錄

> 建立以「購物客服」為首批場景的共用對話框架，後續可擴充諮詢、報修、退換貨、帳務等服務。

---

## 1. 任務目標
- 建立模組化聊天框架，區隔核心流程與場景處理邏輯。
- 先完成購物客服流程的框架落地，確保後續可直接擴充其他客服情境。
- 補齊快取與推薦一致性的基礎能力，避免 session 過期造成體驗落差。

## 2. 範圍與交付物
- **後端架構**：重構會話流程，拆分意圖路由、場景 handler、資料服務層。
- **資料層抽象**：定義購物場景使用的資料介面，預留客服知識庫/FAQ 接口。
- **任務追蹤**：建立推薦套件（Recommendation Bundle）與快取狀態機制的實作計畫。
- **文件與測試**：更新 API 契約、追蹤指標與回歸測試範本。

## 3. 主要里程碑
| 里程碑 | 說明 | 預期時間 |
| --- | --- | --- |
| M1 架構重整 | 完成聊天核心模組化與意圖路由雛型 | T+1 週 |
| M2 購物客服落地 | 完成購物場景 handler、推薦套件持久化、session 流程 | T+2 週 |
| M3 擴充準備 | 補齊監控、測試與文件，預留其他客服情境介面 | T+3 週 |

## 4. 工作分解
1. **聊天框架重構**
   - 定義 Conversation Orchestrator → Intent Router → Scenario Handler 的流程接口。
   - 抽離現有 shopping 專用程式碼，實作 `ShoppingSupportHandler`。
2. **資料層整理**
   - 將商品資料查詢封裝為 `ProductCatalogService`，提供搜尋、推薦、快取能力。
   - 規劃 FAQ/客服知識庫接口（先建立抽象 class，購物場景可回傳空值）。
3. **推薦套件與快取**
   - 設計 Recommendation Bundle schema（含 token、items、meta、有效時間）。
   - 新增 `/api/recommendations/{token}` 端點與快取狀態欄位。
   - 優化前端 fallback 提示（快取過期提醒、重建流程）。
4. **測試與觀測**
   - 建立購物客服流程的自動化測試（LLM mock + API integration）。
   - 定義 session 建立率、快取命中率、LLM 成功率等指標並加入日誌。
5. **文件與交接**
   - 更新聊天流程圖、API 契約與操作手冊。
   - 製作購物客服專用的 SOP 與常見問題處理指南。

## 5. 風險與對策
- **LLM 輸出不穩定**：建立 deterministic mock 回覆，測試與實際流量分離。
- **快取與資料一致性**：推薦套件採持久化儲存，並加入狀態欄位提示前端。
- **擴充成本過高**：框架強制所有場景 handler 遵守統一介面，避免後期重構。

## 6. 後續擴充指引
- 依照 Scenario Handler 標準，新增 `GeneralInquiryHandler`、`RepairHandler` 等模組。
- 導入知識庫或 RAG 時，實作對應的資料服務實體，並掛載到意圖路由。
- 發布新場景前，需補齊測試、觀測項與客服 SOP。
