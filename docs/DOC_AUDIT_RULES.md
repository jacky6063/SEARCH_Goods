# 文件稽核與歸檔規則（DOC_AUDIT_RULES)

目的
- 降低過時文件誤導風險，建立一套可重複執行的「辨識→決策→歸檔→鏈結修補」流程。

判定何謂「過時文件」
- 內容與現況不符（任一條件符合即可視為過時）：
  - 引用已不存在或更名的 API/路由/端點（例如：/api/* 在程式碼找不到）
  - 指示的檔名/路徑/指令不存在或已改名（例如：提到 Netlify 靜態站台，但現行由 FastAPI 提供前端）
  - 依賴的環境變數/旗標在程式中未使用或已改名
  - 前端 UI 元素（ID/按鈕/模式）與現行頁面不符
  - 已被新版文件完整取代（重複/冗餘）

處置原則
- 核心權威文件（README、START_HERE、backend/README、LOCAL_TEST_GUIDE 等）：原則上更新，不歸檔
- 歷史分析/一次性修復/舊部署管線（如 Netlify）等：歸檔
- 歸檔前後，需修補其他文件指向此文件的鏈結

歸檔規則
- 目錄：docs/archive/2025-11/
- 每份歸檔文件檔首加入「Archived banner」：
  - 說明此檔已歸檔（日期/原因）
  - 提供替代/最新文件鏈結（如有）
- 檔名與原檔相同，保留檢索可讀性

建議文件標準欄位（新/更新文件）
- 檔首中繼資料（建議）：
  - 最後核對日期（如：Last-Reviewed: 2025-11-17）
  - 適用版本或 commit（如：main@abcdef1）
  - 關鍵 API/變數/檔案（便於後續自動比對）

執行流程（每輪）
1) 自動掃描（Phase 1）：
   - 建立索引 scripts/doc_index.json（所有 .md）
   - 建立初步偵測 scripts/doc_audit_report.json（疑似失效的 /api 路由清單）
2) 人工複核（Phase 2）：
   - 針對優先清單逐檔決策：保留/更新/歸檔
   - 記錄至 docs/DOC_AUDIT_DECISIONS.md
3) 批次執行（Phase 3）：
   - 將判定為「過時」的文件移至 docs/archive/2025-11/
   - 修補所有指向的相對鏈結
4) 守門機制（Phase 4，可選）：
   - CI/Pre-commit 輕量檢查：若文件含 /api/* 但程式無對應路由，發出警告

注意事項
- 歸檔不等於刪除：仍可從 Git 記錄或 archive 目錄查閱
- 若文件同時包含「過去歷程 + 現行指引」，建議拆分：現行指引保留，歷程移至 archive
