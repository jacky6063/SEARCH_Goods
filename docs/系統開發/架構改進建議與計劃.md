# SEARCH_Goods 架構改進建議與實施計劃

## 📋 執行摘要

根據代碼審查發現，SEARCH_Goods 系統在最近的迭代中出現了以下架構問題：

| 問題 | 嚴重性 | 影響範圍 | 改進工作量 |
|------|--------|---------|-----------|
| God Object (app.py) | 🔴 高 | 可維護性 | 中等（3-5 天） |
| 邊界穿越 | 🔴 高 | 耦合度 | 中等（2-3 天） |
| 無聲的契約破壞 | 🟡 中 | 穩定性 | 低（1-2 天） |
| 提交粒度過大 | 🟡 中 | Review 效率 | 低（流程改進） |

---

## 🔴 優先級 P0: 拆分 app.py (God Object)

### 問題分析

**當前狀態：**
```
app.py: ~2500 行
├─ HTTP 路由層 (app endpoints): ~1000 行
├─ 搜尋業務邏輯: ~400 行  ← 應該在 service
├─ 聊天路由邏輯: ~300 行  ← 應該分離到 chat_router
├─ 管理端點: ~250 行
├─ 層級過濾邏輯: ~150 行  ← 應該在 search_service
└─ 輔助函數: ~400 行      ← 應該分散到各服務
```

**為什麼這是問題：**
1. 每次修改搜尋邏輯，都要進 app.py，污染 HTTP 層
2. 難以測試（需要建立 FastAPI 實例）
3. 難以重用（搜尋邏輯被綁到 HTTP 框架）
4. Code review 困難（500+ 行的變更難以審查）

### 改善方案

#### Step 1: 建立 SearchService 類（1-2 天）

```bash
新建 backend/services/search_service.py

class SearchService:
    def __init__(self, catalog_service: ProductCatalogService):
        self.catalog = catalog_service
    
    # 從 app.py 遷移的方法
    def annotate_hierarchy(self, records, hierarchy)
    def filter_by_hierarchy(self, records, hierarchy)
    def parse_price(self, row)
    def apply_numeric_filters(self, df, filters)
    def search(self, query, topn, required_terms, category_terms)
    
    # 所有搜尋邏輯都在這裡，與 HTTP 無關
```

**效果：**
- app.py 減少 ~200 行
- SearchService 可獨立測試（不需要 FastAPI）
- 搜尋邏輯可在其他地方重用（CLI、批處理等）

#### Step 2: 萃取管理服務（1 天）

```bash
新建 backend/services/admin_service.py

class AdminService:
    def upload_csv(self, file_path, target_path)
    def validate_csv(self, file_path)
    def clear_cache(self)
    def get_system_info(self)
```

**效果：**
- app.py 減少 ~100 行
- 管理邏輯可單獨測試和版本化

#### Step 3: 從 app.py 移除業務邏輯（2 天）

```bash
app.py 改成純路由層：

@app.post("/api/search")
def api_search(req: SearchReq):
    service = SearchService(catalog_service)
    results = service.search(
        query=req.query,
        topn=req.topn,
        ...
    )
    return {"items": results}

@app.post("/api/admin/upload-csv")
def admin_upload(file: UploadFile):
    admin = AdminService()
    admin.upload_csv(...)
    return {"status": "ok"}
```

**效果：**
- app.py 最終 ~1000 行（純路由）
- 所有邏輯移到 service 層
- 更清晰的依賴注入

**驗收準則：**
- ✅ app.py 不超過 1200 行
- ✅ 所有非路由函數 < 20 行
- ✅ 100% 測試覆蓋率（SearchService）

## 🔴 優先級 P0: 清晰的服務邊界

### 問題分析

**當前狀況：**
```
chat_router_goods_action.py 
  ├─ 直接 import goods_search_service
  ├─ 直接呼叫 load_goods_rows() ← 內部實現細節
  ├─ 直接呼叫 search_products(df, ...) ← 暴露 DataFrame
  └─ 假設 goods_search_service 的快取機制 ← 緊耦合

結果：
- 若 goods_search_service 改 API，chat_router 要跟著改
- 難以換成不同的實現（如 Elasticsearch）
```

### 改善方案

**現在的不好做法：**
```python
# chat_router_goods_action.py
from goods_search_service import load_goods_rows, search_products

def _search_products_for_chat(query, keywords):
    df = load_goods_rows()  # 直接訪問內部實現
    results, terms = search_products(df, query)  # 傳入 DataFrame
    return results
```

**改善做法：**
```python
# chat_router_goods_action.py
from services.product_catalog_service import catalog_service

def _search_products_for_chat(query, keywords):
    # 只使用公開的介面
    items = catalog_service.search(query)  # 返回 items
    return items

# services/product_catalog_service.py
class ProductCatalogService:
    def search(self, query, topn=10, hierarchy=None):
        """公開的搜尋介面"""
        df = self.get_dataframe()
        results, _ = search_products(df, query, topn=topn)
        return results  # 返回 item list，不是 DataFrame
    
    # goods_search_service 的實現細節對外隱藏
```

**效果：**
- chat_router 不需要知道 goods_search_service 的存在
- 可以輕易將 search 實現從 CSV 改成 DB
- 所有對 search 的呼叫都通過 catalog_service 中轉

**驗收準則：**
- ✅ chat_router 不直接 import goods_search_service
- ✅ 所有搜尋呼叫都通過 catalog_service
- ✅ DataFrame 不傳出 goods_search_service

## 🟡 優先級 P1: 統一的 API 契約

### 問題分析

**目前的混亂：**
```python
# 不同的地方返回不同格式

# chat_router_goods_action.py
response_v1 = {
    "reply": "...",
    "suggestion_ids": [...],  # 用 IDs
}

# app.py 的聊天端點
response_v2 = {
    "reply": "...",
    "items": [...],           # 用 items
    "structured_products": [...],  # 又有這個
}

# 某次修改
response_v3 = {
    "reply": "...",
    "suggestion_ids": [...],
    "items": [...],           # 為了相容，都保留？
    "structured_products": [...],
}

# 前端不知道用哪個...
```

### 改善方案

**Step 1: 定義唯一的回應契約（1 天）**

```python
# models/chat.py

from pydantic import BaseModel
from typing import Optional, List, Dict, Any

class ChatResponse(BaseModel):
    """聊天 API 回應，保證所有欄位都存在"""
    
    # 必須欄位
    reply: str  # 聊天回覆文字
    
    # 商品相關（互補的資訊）
    suggestion_ids: List[str] = []      # 商品 ID 清單（用於後續查詢）
    items: Optional[List[Dict[str, Any]]] = None   # 商品詳細資訊
    structured_products: Optional[List[Dict[str, Any]]] = None  # 結構化商品資訊
    
    # 互動狀態
    action: Optional[Dict[str, Any]] = None  # 前端應執行的動作
    display_mode: Optional[str] = None  # "text_only" | "products" | "mixed"
    
    # 元資料
    meta: Optional[Dict[str, Any]] = None
    chat_session_id: Optional[str] = None
    
    class Config:
        # 示例值（用於文檔生成）
        schema_extra = {
            "example": {
                "reply": "我為您找到 3 款橄欖油...",
                "suggestion_ids": ["prod_001", "prod_002"],
                "items": [{"id": "prod_001", "name": "特級初榨橄欖油"}],
                "display_mode": "products",
                "action": {"type": "switch_to_search"},
            }
        }

# 確保所有 API 返回此類型
@app.post("/api/chat", response_model=ChatResponse)
def chat_endpoint(req: ChatReq) -> ChatResponse:
    # Pydantic 會驗證回傳值，缺少欄位會拋出詳細錯誤
    pass
```

**Step 2: 在所有回應生成點應用（1 天）**

```python
# chat_router_goods_action.py

def _finalize_directional_products(...) -> ChatResponse:
    # 明確返回 ChatResponse 型別
    return ChatResponse(
        reply=reply,
        suggestion_ids=suggestion_ids,
        items=structured_products,
        display_mode="flat",
        action={"type": "none"},
    )

def _finalize_text_only_fallback(...) -> ChatResponse:
    # 所有程式碼路徑都回傳同一類型
    return ChatResponse(
        reply=reply,
        suggestion_ids=[],
        display_mode="text_only",
        action={"type": "none"},
    )
```

**效果：**
- 前端永遠知道有哪些欄位
- IDE 可提供自動完成
- 測試可驗證所有欄位都存在

**驗收準則：**
- ✅ 所有 /api/chat 回傳都使用 ChatResponse
- ✅ 沒有硬編碼的字典，使用 ChatResponse(...)
- ✅ 缺少必須欄位會在開發時就報錯

**現在的提交：**

## 🟢 優先級 P2: 環境配置改進

### 問題分析

**現況：**
```python
# 多個地方有重複的環境檢測邏輯
# app.py 和 goods_search_service.py 都有這個：

def _get_csv_path():
    render_path = Path("/opt/render/project/src/data/...")
    if render_path.exists():
        return render_path
    return ROOT / "data" / "..."

# 結果：
# 1. 代碼重複
# 2. 若要改邏輯，要改兩個地方
# 3. Render 路徑寫死，難以擴展
```

### 改善方案

**Step 1: 集中配置管理（1 天）**

```python
# backend/config.py

from pathlib import Path
import os
from typing import Optional

class AppConfig:
    """應用配置管理（支援多環境）"""
    
    @staticmethod
    def get_data_path() -> Path:
        """獲取 CSV 資料檔案路徑，支援多層 fallback"""
        
        # 優先級 1: 環境變數
        if env_path := os.getenv("DATA_PATH"):
            path = Path(env_path)
            if path.exists():
                return path
            else:
                raise FileNotFoundError(f"DATA_PATH={env_path} 不存在")
        
        # 優先級 2: Render 生產環境
        paths_to_check = [
            Path("/opt/render/project/src/data/VIEW_GOODS_enhanced.csv"),
            Path("/opt/render/project/src/backend/data/VIEW_GOODS_enhanced.csv"),
        ]
        for path in paths_to_check:
            if path.exists():
                return path
        
        # 優先級 3: 本地開發
        local_path = Path(__file__).parent / "data" / "VIEW_GOODS_enhanced.csv"
        if local_path.exists():
            return local_path
        
        # 都找不到，回報詳細的錯誤
        raise FileNotFoundError(
            f"CSV file not found. Checked:\n"
            f"  ENV: {os.getenv('DATA_PATH')}\n"
            f"  Render: {paths_to_check[0]}\n"
            f"  Local: {local_path}\n"
            f"Set DATA_PATH environment variable."
        )
    
    @staticmethod
    def is_production() -> bool:
        """判斷是否運行在生產環境"""
        return os.getenv("ENVIRONMENT") == "production"
    
    @staticmethod
    def is_development() -> bool:
        """判斷是否運行在開發環境"""
        return os.getenv("ENVIRONMENT", "development") == "development"
```

**Step 2: 統一使用配置（1 天）**

```python
# app.py
from config import AppConfig

DATA_PATH = AppConfig.get_data_path()

# goods_search_service.py
from config import AppConfig

DEFAULT_DATA_PATH = AppConfig.get_data_path()

# llm_service.py
from config import AppConfig

if AppConfig.is_production():
    OPENAI_MODEL = "gpt-4"
else:
    OPENAI_MODEL = "gpt-3.5-turbo"
```

**效果：**
- 環境檢測邏輯集中在一個地方
- 新增環境時只需修改 config.py
- 更容易測試環境相關的邏輯

**驗收準則：**
- ✅ _get_csv_path() 只在 AppConfig 中定義
- ✅ 所有環境相關邏輯都使用 AppConfig
- ✅ 支援 ENVIRONMENT 環境變數
