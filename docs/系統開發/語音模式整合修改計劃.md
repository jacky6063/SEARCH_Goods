# 語音模式整合修改計劃

> 更新日期：2025-11-10  
> 撰寫人：Codex（依現況檢視與使用者要求彙整）

## 1. 目標
- 修復近期 refactor 造成的語音模式功能缺口，確保基本體驗可用。
- 重新對齊《語音模式整合設計》文件與實際程式碼，並為下一階段擴充建立清晰待辦。
- 建立可持續維運的語音模式架構（Whisper-only 亦或多供應商），避免日後再次偏離規格。

## 2. 現況問題摘要
| 編號 | 類別 | 問題描述 | 影響 |
| --- | --- | --- | --- |
| P1 | 前端 | `scrollChatToBottom()` 被刪除但多處仍呼叫，語音/聊天流程直接崩潰。 | Critical：按鈕點擊即報錯，阻擋所有互動。 |
| P2 | 前端 | 管理面板僅剩 `voice_mode_enabled`，UI 仍聲稱可用於「STT 成本評估」，導致與需求方預期不符。 | High：產品溝通失真。 |
| P3 | 後端 | `config_store.py`、`voice_service.py`、`.env.example` 全面移除 Google/Azure STT 支援，未留降級策略或文檔更新。 | High：若營運仍需多供應商，功能實際消失。 |
| P4 | 規格差距 | 文件要求「前端意圖初篩 + 後端白名單」但實作只剩後端判斷；`/api/voice/chat` 端點未被使用。 | Medium：成本上升、文檔與程式不一致。 |
| P5 | UX/隱私 | 文件規定需顯示「僅即時轉文字、不留錄音」提示與清楚錯誤訊息，目前 UI 只用狀態列暫時顯示，缺乏常駐說明。 | Medium：隱私告知不足。 |
| P6 | 可觀測性 | 尚未實作 voice-session 指標或事件上報，無法評估使用率、拒絕率、平均時長。 | Low/Medium：影響後續調優。 |

## 3. 調整原則
1. **先穩定、再優化**：優先修復 runtime error 與體驗崩潰，再處理規格與擴充。
2. **與文件同步**：任何功能增刪必須同步更新《語音模式整合設計》及相關 README/流程圖。
3. **保留擴充彈性**：即使暫時只支援 Whisper，也需在架構上保留擴充點（節點、介面、設定儲存格式）。
4. **量化效果**：導入最少可行的指標/事件，以便後續檢驗語音模式成效。

## 5. 依賴與風險
- **需求確認**：是否真的不再需要 Google/Azure STT？若決策延遲，Phase 1 之後工作無法展開。
- **瀏覽器權限**：iOS Safari 對 MediaRecorder 支援有限，可能需要額外 fallback。
- **LLM 成本**：語音模式會增加查詢量，需要與後端成本控制策略協調。
