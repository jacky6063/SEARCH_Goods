系統開發應遵循以下三層架構：

```

   ↓
層級 3: 驗收與優化 (Validation Phase)
```

## ❌ 不應該犯的錯誤

### 錯誤 1: "God Object" 反模式 (Observed in app.py)

**問題描述：**
```python
# ❌ 在 app.py 中堆砌各種邏輯
class app(FastAPI):
    def _annotate_hierarchy(...)  # 搜尋相關
    def _filter_by_hierarchy(...)  # 搜尋相關
    def _parse_price(...)          # 搜尋相關
    def _extract_ids_from_items(...) # 回應格式化
    def _filter_on_sale(...)       # 業務邏輯
    # ... 20+ 個私有函式和 10+ 個端點路由

# 結果：
# - app.py 變成 2000+ 行的怪物檔案
# - 想修改搜尋邏輯，卻在 app.py 中操作
# - 想修改聊天路由，卻影響搜尋邏輯
```

**改善方案：**
```python
# ✅ 將職責分散到專用服務

# services/search_service.py
class SearchService:
    def _annotate_hierarchy(...)
    def _filter_by_hierarchy(...)
    def _parse_price(...)

# services/chat_service.py
class ChatService:
    def _compose_response(...)
    def _extract_ids(...)

# app.py
from services.search_service import SearchService
from services.chat_service import ChatService

@app.post("/api/search")
def api_search(req: SearchReq):
    service = SearchService()
    return service.search(req)
```

```python
# ✅ 環境相關配置應該有多層 fallback

def _get_csv_path():
    """自動檢測並返回正確的 CSV 文件路徑"""
    # 第1層：環境變數（最高優先級）
    env_path = os.getenv("DATA_PATH")
    if env_path and Path(env_path).exists():
        return Path(env_path)
    
    # 第2層：已知的生產路徑
    render_path = Path("/opt/render/project/src/data/VIEW_GOODS_enhanced.csv")
    if render_path.exists():
        return render_path
    
    # 第3層：默認本地開發路徑
    default_path = ROOT / "data" / "VIEW_GOODS_enhanced.csv"
    if default_path.exists():
        return default_path
    
    # 第4層：詳細的錯誤信息幫助除錯
    raise FileNotFoundError(
        f"CSV file not found. Checked:\n"
        f"  1. {env_path}\n"
        f"  2. {render_path}\n"
        f"  3. {default_path}\n"
        f"Please set DATA_PATH environment variable or ensure file exists."
    )

DATA_PATH = _get_csv_path()
```

```python
# ✅ 清晰的命名、參數、文檔

def finalize_as_text_only_response(
    base_response: Dict[str, Any],
    override_reply: Optional[str] = None,
    additional_meta: Optional[Dict[str, Any]] = None,
) -> ChatResponse:
    """
    轉換回應為純文字模式（不含商品卡）。
    
    用途：當無法找到商品或需要回退時，保證回應仍然有效。
    
    Args:
        base_response: 基礎回應字典
        override_reply: 若提供，使用此回覆而非 base_response.reply
        additional_meta: 要附加（不是覆蓋）到 meta 的欄位
    
    Returns:
        ChatResponse: 已驗證的回應物件，保證包含所有必須欄位
    
    Example:
        >>> resp = finalize_as_text_only_response(
        ...     {"reply": "...", "meta": {}},
        ...     override_reply="新回覆",
        ...     additional_meta={"source": "fallback"}
        ... )
        >>> assert resp.display_mode == "text_only"
        >>> assert resp.suggestion_ids == []
    """
    combined_meta = {**(base_response.get("meta") or {})}
    if additional_meta:
        combined_meta.update(additional_meta)
    
    return ChatResponse(
        reply=override_reply or base_response.get("reply", ""),
        suggestion_ids=[],
        display_mode="text_only",
        action={"type": "none"},
        meta=combined_meta,
    )
```

## 🔍 真實案例分析

### 案例：search_goods 特性的正確實現

#### 背景
需求：支援 L1/L2/L3 三層商品分類，搜尋時優先過濾層級相符的商品。

#### ❌ 不好的實現方式（實際修改中出現過的問題）

**問題 1：多個檔案同時大量修改**
```
修改範圍太廣：
  - app.py: +250 行（搜尋邏輯、層級過濾、管理端點）
  - goods_search_service.py: +180 行（評分改進、CatePath 建立）
  - chat_router_goods_action.py: +200 行（回退邏輯、OOS 守門）
  - llm_service.py: +150 行（意圖判斷、分類層級提示詞）

結果：impossible to review properly, risk of regression
```

**問題 2：向後相容性破壞**
```python
# 舊版回應格式
{
    "items": [
        {"id": "...", "name": "...", "price": "..."}
    ]
}

# 新版本（沒想到要相容）
{
    "items": [...],
    "structured_products": [...],  # 新增
    "matched_levels": [...],        # 新增
    "hierarchy_score": 0
}

# 問題：舊前端只讀 "items"，不知道新欄位，
# 但新前端期望 "structured_products" 存在
```

#### ✅ 正確的實現方式

**第一步：需求文檔化**
```markdown
# L1/L2/L3 分類支援

## 需求
- 搜尋時若 LLM 識別出分類（L1/L2/L3），優先過濾相符商品
- 回應中帶回匹配的層級資訊（matched_levels、hierarchy_score）

## 受影響模組
1. goods_search_service.py - 搜尋評分增強
2. llm_service.py - 分類層級提取
3. app.py - /api/search 端點整合
4. chat_router_goods_action.py - 聊天模式的層級支援

## API 契約變更
- /api/search 回應新增：
  - items[].matched_levels: ["L1"] | ["L1", "L2"] | []
  - items[].hierarchy_score: int
  - （都有預設值以保持向後相容）
```

**第二步：分解成獨立可交付的提交**

```bash
提交 1: goods_search_service.py - 基礎層級支援
├─ 新增 CatePath 欄位建立
├─ 新增 _annotate_hierarchy() 函數（私有）
├─ 修改 format_for_chat() 回傳層級資訊
└─ 單元測試：測試層級標註和回傳

提交 2: llm_service.py - 分類提取能力
├─ 新增 _build_category_hierarchy_prompt()
├─ 修改 llm_analyze_query() 回傳 category_hierarchy
└─ 單元測試：測試意圖判斷和層級提取
```

## 📚 參考資源

### 設計模式
- **Service Layer Pattern**: 將業務邏輯與 HTTP 層分離
- **Repository Pattern**: 統一的數據訪問介面
- **Feature Branch Workflow**: 按功能分支，便於 review 和管理

### 工程實踐
- **Semantic Versioning**: 版本號有含義，便於追蹤 breaking change
- **API Versioning**: /api/v1/..., /api/v2/... 便於過渡
- **Contract Testing**: Pydantic BaseModel 強制 API 契約

### 測試策略
- **Test Pyramid**: Unit > Integration > E2E（數量比例）
- **Acceptance Test Driven Development**: 先寫測試，再寫代碼
- **Property-based Testing**: 用生成的隨機輸入測試
