# 聊天資訊流規範

本文整理從使用者輸入到「按 1 顯示商品卡」的完整流程，方便系統開發與除錯。流程被拆成前端、後端與共用快取三個層面，並列出關鍵函式與資料欄位。

## 1. 前端流程（`frontend/index.html`）

1. **送出訊息** – `sendChat()`（約第 810 行）收集文字、裁剪 `history`，POST `/api/chat`。
2. **解析回應** – `stripIntentPayload()` 將回覆內嵌 JSON 與顯示文字分離，取出 `structuredPayload`。
3. **整合商品資料**
   - `structuredItems`：優先使用內嵌 JSON；若無則 fallback 至 `data.structured_products`。
   - `payloadItems`：順序為 `data.items` → `data.structured_products`，保證 fallback 搜尋仍有商品陣列。
4. **寫入快取** – `setSuggestCache(1, payloadItems, {...})` 將商品卡存入 `latestSuggestCache[1]`，附加 summary、meta、sessionId。
5. **顯示狀態**
   - 若 `meta.search_fallback = true` 且無商品 → 清空 `latestSuggestCache`、顯示提醒。
   - `directional_products = true` 或 `payloadItems` 有值 → 允許顯示商品卡。
6. **按 1 顯示商品卡** – `handleSuggestTrigger()` 讀取 `latestSuggestCache[1]`，若有效即呼叫 `switchToSearch()` 展示卡片；無效則提示重新詢問。

## 2. 後端流程（`backend/chat_router_goods_action.py`）

1. **API 入口** – `chat_handler()` 建立 `ConversationInput`，交給 `_ORCHESTRATOR.handle()`。
2. **意圖判定** – `_legacy_chat_flow()` 呼叫 `planner_detect_intent()`、判斷 `party_context`、`has_budget_intent()`。
3. **路由**
   - `shopping_recommender.prepare_shopping_response()`：處理購物意圖、整合 `suggestion_ids`、`structured_payload`，必要時啟動 Category Planner。
   - `marketing_consultant.prepare_information_response()`：資訊導購意圖；預設只回傳文字，若 LLM 附帶商品 JSON 會存於 `meta.info_preview` 並用 `_strip_structured_suffix()` 去除尾段 JSON。
4. **Fallback 順序**
   1. `_finalize_directional_products()` – 搜尋命中商品，生成卡片並寫入快取。
   2. `_finalize_text_only_fallback()` – 純文字建議，清空商品欄位、顯示狀態訊息。
   3. 其他擴充策略（增強 mock、simple handler）。
5. **回傳** – 最終以 `ChatResponse` 回傳 `reply`、`suggestion_ids`、`meta`、`structured_products` 等欄位。

## 3. 快取與資料供應

| 名稱 | 位置 | 主要職責 |
| --- | --- | --- |
| `CHAT_SESSION_CACHE` | `backend/chat_router_goods_action.py` | 以 `session_id` 快取聊天結果（商品卡、meta 等）供建議按鈕與 `/api/chat-session` 讀取。 |
| `RecommendationBundleService` | `backend/services/recommendation_bundle_service.py` | 保存推薦卡片的 `align_ids`、`structured_items`，新增 `_cleanup_interval` 以定期清理。 |
| `ProductCatalogService` | `backend/services/product_catalog_service.py` | 以雙重檢查鎖管理 CSV DataFrame，`get_items_by_ids()` 補齊商品欄位。 |

## 4. 重要欄位與旗標

- `meta.search_fallback = true`：純文字方向建議；前端需清空快取與商品卡。
- `meta.directional_products = true`：可顯示商品卡（多為 fallback 搜尋命中）。
- `structured_products` / `items`：商品卡資料來源，前端 `payloadItems` 主要依據。
- `latestSuggestCache[type]`：瀏覽器端建議快取；`type=1` 對應按 1 的「原建議」。

## 5. 開發建議

1. 當新增回覆類型時，先定義好 `meta` 旗標與 `items` 填值策略，再同步更新前端快取邏輯。
2. 任何 fallback 調整應同時檢查：
   - 有無寫入 `CHAT_SESSION_CACHE`（供建議 API 使用）。
   - `structured_products` / `items` 是否符合預期。
3. 若觸發「按 1 無商品卡」問題，檢查順序建議為：
   1. 前端 Network 查看 `/api/chat` 是否帶 `items`/`structured_products`。
   2. 確認 `latestSuggestCache[1]` 是否被覆蓋或清空。
   3. 檢視後端對應的 fallback 分支是否走 `_finalize_text_only_fallback()`。

透過以上規範，可迅速定位聊天 → 推薦 → 按鍵的資訊流，降低前後端協作時的誤判與反覆修改。
