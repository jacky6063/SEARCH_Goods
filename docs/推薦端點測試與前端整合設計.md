# `/api/recommendations/{token}` 測試與前端整合設計

> 目標：在導入持久化之前，先確保新的推薦端點與記憶體快取流程完整可測、可供前端使用。

---

## 1. 整合測試設計

### 1.1 測試案例

| 案例 | 說明 | 驗證要點 |
| --- | --- | --- |
| **T1. 建立 Bundle 後成功取得** | 透過 `/api/chat` 或直接呼叫內部 helper 產生推薦套件，再以 `/api/recommendations/{token}` 取得資料 | - 回傳 `status: "ok"`<br>- `bundle_id` 與請求 token 一致<br>- `items/products` 長度與建立時吻合<br>- `suggestion_type` 預設為 1 (`original`) |
| **T2. view 切換** | 使用 `view=sale`、`view=complementary` 參數 | - 轉換成對應 `suggestion_type`（2、3）<br>- 回傳的清單與 `_build_suggestion` 驗證一致（例如當 `structured_items` 有特價商品時）|
| **T3. explicit suggestion_type** | 以 `?suggestion_type=2` 呼叫 | - 優先使用 `suggestion_type`，無論 `view` 是否傳入 |
| **T4. 快取過期** | 手動調整 `bundle_service` 或修改儲存內容的 `ts` 讓 `_render_bundle_response` 判定為過期 | - 回傳 `status: "expired"` / `mode: "chat"`<br>- `items/products` 為空<br>- `message` 有提示 |
| **T5. 無效 token** | 直接呼叫不存在的 bundle | - 同 T4，視為過期並回傳 `status: "expired"` |

### 1.2 測試實作建議
- 在 `backend/tests/test_api.py` 或新增 `test_recommendations_api.py` 中撰寫。
- 建議建立 fixture/helper：
  - `create_bundle(session_id, payload)`：使用 `bundle_service.save_bundle` 模擬聊天結果。
  - `call_recommendations(client, bundle_id, **params)`：統一呼叫 API 並檢查狀態碼。
- 使用 `time.time()` patch 或 bundle payload 中的 `ts` 欄位調整過期情境。
- 需覆蓋 `/api/suggest` 與新端點結果一致的情境（可比較字段）。

## 2. 前端與腳本調整

### 2.1 參數與流程
- 前端按鈕（原本呼叫 `/api/suggest`）現改為：
  1. 優先使用 `/api/recommendations/{bundle_id}?view={view}`。
  2. 若回傳 `status: "expired"`，顯示提示「推薦已過期，請重新詢問」或自動觸發上次訊息重播。
  3. 保留 `/api/suggest` 作向後相容（若 bundle_id 缺失或 view 需要 type 參數）。
- `bundle_id` 來源：聊天回傳的 `chat_session_id`（既有欄位）；前端需在本地存起來（state/store）。
- `view` 對應：
  - `1` → `original`
  - `2` → `sale`
  - `3` → `complementary`
- 若前端還需舊模式，可在呼叫 `/api/suggest` 時帶 `type=1/2/3` 作 fallback。

### 2.2 回傳欄位對應
- 新端點回傳：
  ```json
  {
    "status": "ok",
    "bundle_id": "abcd1234",
    "suggestion_type": 1,
    "view": "original",
    "items": [...],
    "products": [...],
    "message": "...",
    "assistant_reply": "..."
  }
  ```
- 前端只需改用 `items/products` 渲染，並檢查 `status` 決定顯示或提示。
- `status != "ok"` 時，原本 fallback 熱門商品的行為應改為顯示提示，避免回到不一致的推薦。

### 2.3 手動測試腳本
- `curl` 範例：
  ```bash
  curl "http://localhost:8000/api/recommendations/abcd1234?view=sale"
  curl "http://localhost:8000/api/recommendations/abcd1234?suggestion_type=3"
  ```
- 快取過期測試：
  1. 正常呼叫得到資料。
  2. 透過管理端 `POST /api/admin/clear-cache` 或直接調整 `bundle_service.raw_store()` 使其過期，再呼叫端點檢查 `status: "expired"`。

---

## 3. 實作順序
1. **測試**：先加入單元/整合測試，確保新端點與過期邏輯的行為受控。
2. **前端 / 腳本調整**：將按鈕、簡化腳本改用新端點，加入 `status` 判斷。
3. **清理與文件**：更新 API 文件（`docs/API接口規範.md`）與部署手冊，提醒使用者帶 token / view。

完成以上後，再進行持久化實作時即可直接覆用既有測試與前端邏輯。對 PostgreSQL 版本而言，端點行為不需更改，只要 bundle service 從記憶體換成資料庫即可。
