# 推薦套件（Recommendation Bundle）資料需求與存取流程

> 目標：把現有的記憶體快取整理成可持久化的結構，支援多實例部署、重啟復原，以及後續客服情境的統一資料來源。

---

## 1. 欄位需求

| 欄位 | 型別 | 說明 | 備註 |
| --- | --- | --- | --- |
| `bundle_id` | string | 推薦套件唯一識別碼（UUID 或 short token） | 可與 `session_id` 共用，或額外生成 |
| `session_id` | string | 聊天會話識別，提供前端沿用 | 舊流程以 8 碼 UUID 前綴 |
| `intent_type` | string | 觸發意圖，例如 `shopping_support`、`information` | 便於後台分析與擴充情境 |
| `source_message` | string | 觸發推薦的原始用戶訊息 | 追蹤問題來源、復播時可提示 |
| `query_terms` | string[] | 模型推斷出的查詢關鍵詞 | 目前僅紀錄 `[user_text]`，可擴充 |
| `structured_items` | JSON[] | LLM 輸出的結構化商品清單 | 字段包含 `商品編號/名稱/描述/價格...` |
| `structured_summary` | string | LLM 提供的摘要文案 | `/api/suggest` 回 fallback 用 |
| `align_ids` | string[] | 供 `/api/suggest` 讀取的商品 ID 序列 | 與 `align_rows` 或 `products_cache` 對應 |
| `products_cache` | JSON[] | 從資料庫撈出的商品原始資料快照 | 避免重查；長期可壓縮為精簡欄位 |
| `structured_filters` | JSON | 聊天推導出的過濾條件 | 目前包含價位/類別等 |
| `display_mode` | string | 前端渲染模式：`flat`、`grouped` 等 | 舊流程 `display_mode` 已使用 |
| `meta` | JSON | 其他補充資訊（LLM 版本、confidence 等） | 保留擴充空間 |
| `status` | enum | `active` / `expired` / `invalid` | 快取查無時可回報前端 |
| `version` | int | 資料版本號 | schema 調整時便於遷移 |
| `created_at` | datetime | 建立時間 | 便於追蹤與 TTL 計算 |
| `expires_at` | datetime | 過期時間 | `created_at + TTL` 或外部設定 |
| `last_access_at` | datetime | 最後讀取時間 | 可用於延長 TTL 或分析熱度 |

### JSON 範例
```json
{
  "bundle_id": "d4f7a21b",
  "session_id": "d4f7a21b",
  "intent_type": "shopping_support",
  "source_message": "想找 2000 元內的防水後背包",
  "query_terms": ["防水", "後背包", "2000 元"],
  "structured_items": [
    {"商品編號": "A123", "商品名稱": "防水旅用後背包", "商品特價": "1890", "商品圖片網址": "..."}
  ],
  "structured_summary": "幫您挑選了 3 款防水後背包，預算都在 2000 元以內。",
  "align_ids": ["A123", "A456", "A789"],
  "products_cache": [
    {"GoodIden": "A123", "Name": "防水旅用後背包", "Price": "2200", "SpecialOffer": "1890", ...}
  ],
  "structured_filters": {"price": [{"max": 2000}]},
  "display_mode": "flat",
  "meta": {"llm_model": "gpt-4o-mini-2025-10"},
  "status": "active",
  "version": 1,
  "created_at": "2025-10-31T10:20:30Z",
  "expires_at": "2025-10-31T10:30:30Z",
  "last_access_at": "2025-10-31T10:21:05Z"
}
```

## 2. 存取流程

### 2.1 建立（Create）
1. 聊天流程完成推薦後，handler 呼叫 `bundle_service.save_bundle(bundle_id, payload)`。
2. 服務層補上 `created_at` / `expires_at` / `ts`（或 `last_access_at`）後寫入儲存層。
3. 回傳 `bundle_id` 給前端，前端按鈕與後續 API 攜帶同一識別碼。

### 2.2 讀取（Read）
1. `/api/suggest` 或未來的 `/api/recommendations/{bundle_id}` 讀取時，先觸發 `bundle_service.cleanup()` 清掉過期資料。
2. 若讀到資料，更新 `last_access_at`（視需求延長 TTL）。
3. 做資料格式化：若 `products_cache` 有值直接回傳；否則再透過 `ProductCatalogService` 依 `align_ids` 補齊。
4. 若讀不到資料，回傳 `status: "expired"` 或 `mode: "chat"` 提醒前端。

### 2.3 更新（Update）
1. 聊天再度調整推薦時，直接覆蓋同一 `bundle_id` 或生成新 token。
2. 若需延長活躍 session，可在使用者互動時更新 `expires_at` / `last_access_at`。

### 2.4 清除（Cleanup）
1. 排程或啟動時呼叫 `bundle_service.cleanup()`，刪除 `expires_at` 已過的資料。
2. 管理端提供 API（如 `/api/admin/clear-cache`）重設儲存層，或依條件清除指定 bundle。

## 3. 持久化實作考量

| 選項 | 優點 | 風險 / 注意事項 |
| --- | --- | --- |
| Redis / Key-Value | TTL 支援、效能佳，資料結構簡單 | 需設計壓縮格式（例如 hash + JSON）；要處理多欄位更新 |
| PostgreSQL / SQLite | 結構化查詢、易追蹤歷史紀錄 | 需自行管理 TTL / 清理；高併發時要注意鎖 |
| 混合（Redis 作快取 + DB 作歷史） | 讀寫快、可追蹤歷史 | 開發成本較高，需要同步機制 |

建議先以 Redis（或 SQLite）實作 MVP：
- Key：`bundle:{bundle_id}`
- Value：JSON (或 hash)
- TTL：`expires_at - now`，更新時重設 TTL
- 若需追蹤歷史，可定期將 key dump 至長期儲存（DB / S3）。

## 4. 後續工作清單
1. **介面定義**：將 `RecommendationBundleService` 介面化，預留 `RedisRecommendationBundleService`、`MemoryRecommendationBundleService`。
2. **API 調整**：新增 `/api/recommendations/{token}`；舊 `/api/suggest` 攜帶 `bundle_id` 與 `view` 參數。
3. **結構驗證**：撰寫單元測試檢查儲存與讀取流程、TTL 行為、結構化資料完整性。
4. **監控指標**：記錄 bundle 建立數量、命中率、過期率，作為客服體驗觀測。
5. **安全性**：bundle_id 長度與entropy要足夠，避免被猜測；若與 session cookie 結合需考慮權限驗證。

---

> 以上資料需求與流程請作為後續定義資料庫 schema 與 API 調整的依據。如需擴充客服情境，只要在 `structured_items`、`meta` 中對應欄位即可維持兼容性。
