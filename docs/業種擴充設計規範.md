# 業種/業態擴充設計規範

最後更新：2025-11-16  
撰寫者：SEARCH_Goods 團隊

---

## 1. 目標
- 以最小成本導入新的商品業種/業態（例如：家電、家具、生鮮）。
- 確保聊天、搜尋、行銷文案等模組只需配置即可生效，減少硬寫條件。
- 維持真人導購體驗，任何新 vertical 都能以既有流程快速驗證上線。

---

## 2. 架構原則
1. **資料驅動**：分類結構、同義詞、關鍵字、語氣等都放在設定檔或資料表，程式僅讀取與快取。
2. **模組化 Handler**：ConversationOrchestrator + IntentRouter 固定，新增業種若需要特殊流程，就新增 Handler。
3. **統一服務層**：商品/分類/內容生成透過 `catalog_service`、`content_engine` 等服務取得標準欄位。
4. **清楚的可觀測性**：所有 log 需帶 `session_id` / `intent`，方便追蹤新業種的狀況。
5. **分階段 rollout**：以 config flag 控制新業種，先在 staging / 灰度環境驗證，再全面開啟。

---

## 3. 資料層設計

### 3.1 分類與同義詞
- **來源**：`data/taxonomy/*.csv` 或 JSON，可由營運/PM 維護。
- **欄位**：`L1`, `L2`, `L3`, `aliases`, `keywords`, `display_name`, `vertical`。
- **流程**：
  1. 更新 taxonomy 檔案，新增 vertical 所需的 L1-L3 與同義詞。
  2. 執行 `catalog_service.refresh()` 或對應 ETL 任務，使快取與 search index 更新。
  3. 在 `services/search_service` 中同步新的 negative/positive keyword 規則（如需要）。

### 3.2 Vertical Config
建立 `config/verticals/<vertical>.json`，內容示例：
```json
{
  "name": "lifestyle_fashion",
  "persona_prompt": "...",
  "tone": "溫柔、貼心",
  "top_categories": ["時尚女性", "日常配件"],
  "featured_levels": {
    "背包": ["通勤", "旅行", "輕量"],
    "運動鞋": ["慢跑", "訓練", "戶外"]
  },
  "fallback_phrases": {
    "clarify": "想知道更具體的用途嗎？像是通勤、旅行或送禮？"
  }
}
```
程式在啟動時載入 config 並快取，聊天流程依照目前 vertical 決定語氣、提示字詞、熱門分類。

## 4. 對話/聊天層

### 4.1 意圖偵測 + Handler
- `ConversationOrchestrator` 固定，新增業種若需要特定動作（例如家電維修）就新增 `XxxHandler`，並在 `IntentRouter.register()` 載入。
- 建議透過 env 或設定檔啟用：
  ```python
  if vertical_config.get("handlers", {}).get("repair"):
      _INTENT_ROUTER.register("repair_support", RepairHandler())
  ```

### 4.2 分類導覽 / 真人回覆
- `_try_category_navigation_reply` 與 `_try_overview_scope_reply` 必須參考 taxonomy，根據使用者輸入自動決定要列 L1/L2/L3。
- 若偵測到具體分類（例如「運動鞋」對應 L2），回覆格式：
  ```
  「運動鞋」目前細分為：慢跑鞋、訓練鞋、戶外鞋。
  想先看哪一類？是平日通勤還是專業運動呢？
  ```
- 若找不到對應 L3，回覆 L2 並附上真人語氣的澄清問句；同時記錄 log 以便後續補 taxonomy。

### 4.3 範例 (偵測流程)
1. 使用者輸入：「想看女用背包」
2. `taxonomy_service.match("女用背包")` → L2: 女用包, L3: 通勤 / 旅行 / 輕量
3. 回覆：
   ```
   女用背包目前有通勤、旅行、輕量三種風格，
   想先看看哪一種？還是有特別的場合要搭配？
   ```
4. 若使用者回答「通勤」，就帶入 `structured_filters`，後續 LLM 搜尋只看 L3=通勤背包。

---

## 5. 服務層整合

### 5.1 Catalog / Content Engine
- 任何新業種先確保 CSV 欄位與 `FieldAccessor` (商品名稱、價格、分類、描述等) 對齊，必要時在 `FIELD_MAPPINGS` 新增別名。
- Content Engine (生成 SEO、賣點) 透過 configuration 知道不同 vertical 要使用的模板（例如：家電強調功率、保固；美妝強調成分、膚質）。

### 5.2 搜尋 / Negative Keywords
- `services/search_service` 中維護 `negative_keywords`、`min_score` 等規則，可依 vertical 擴充。
- 若新業種需要自訂 emb 模型或分數門檻，建議在 config 內定義 `search_profile`，例如：
  ```json
  "search_profile": {
    "min_score": 0.6,
    "embedding_model": "text-embedding-3-large"
  }
  ```

---

## 6. Log 與監控
- 所有 log 維持 structured format（`session_id`, `intent`）。
- 新 vertical 上線前建立 Dash/Alert 項目：
  - 意圖命中率 (`intent=vertical_x_support` 百分比)。
  - 澄清率 (`meta.clarify=True`)。
  - Fallback 次數 (`meta.search_fallback`)。
- 若要快速診斷，可為每個 vertical 設置 `DEBUG_VERTICAL=<name>` env，啟用額外 log（比如顯示 match 到的 L3、Planner 結果）。

---

## 7. 測試策略

### 7.1 手動驗證清單
1. **語氣**：輸入 3~5 種常見問法，確認回覆符合 persona。
2. **分類導覽**：測試 L1/L2/L3 詢問，確保能列出對應細節。
3. **商品查詢**：輸入完整需求（用途 + 預算），需拿到 structured_products 並有正確 `structured_filters`。
4. **澄清/負向關鍵字**：輸入不販售品項，確認能跳出澄清文案。
5. **語音模式 (若啟用)**：確認 `voice_summary` 基於新 vertical 的文案。

### 7.2 自動化測試建議
- 新增 `tests/test_vertical_<name>.py`，透過 fixture 載入示例 taxonomy。
- 測試 `_try_category_navigation_reply` 回傳內容是否包含對應 L3。
- 模擬 `/api/chat` 請求，驗證 `structured_products` 與 `meta` 是否符合預期。
- 若有特殊 handler，為該 handler 撰寫單元測試，確保 `can_handle` / `handle` / `fallback` 行為正確。

---

## 8. Rollout 流程
1. **定義 config**：建立 taxonomy + vertical config，於 staging 驗證。
2. **局部啟用**：設定 `VERTICALS_ENABLED=["fashion","new_vertical"]`，只對指定客戶或環境開啟。
3. **監控**：上線後一週密切觀察 log（澄清率、fallback、錯誤），必要時快速調整 taxonomy 或 prompt。
4. **擴散**：確認穩定後，在主環境開啟，並更新文件/操作手冊。

---

## 9. Checklist（新增業態前必讀）
- [ ] taxonomy 檔案中已新增 L1-L3 與 aliases。
- [ ] vertical config 內的人格、語氣、熱門分類已設定。
- [ ] FieldAccessor 已支援該業態的欄位差異。
- [ ] Conversation handler / router 設定完成，必要時加上 feature flag。
- [ ] 手動測試 5 個案例（詢問、導覽、商品卡、澄清、語音）。
- [ ] 監控與 log 設定已更新（Dashboard/Alert）。
- [ ] rollout 策略（時間、灰度對象）已確認。
