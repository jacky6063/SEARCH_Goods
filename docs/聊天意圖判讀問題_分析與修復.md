# 聊天意圖判讀問題 - 分析與修復方案

## 📋 問題描述

### 使用者測試情境

1. ✅ **公司查詢 + 商品查詢**: 可以自由判讀切換
2. ❌ **對話中插入住宅維修**: 當前面有對話資料時，輸入住宅維修關鍵字無法正確判讀

---

## 🔍 問題根本原因分析

### 當前系統架構

系統有**兩層意圖判讀**機制：

#### 1️⃣ **前端意圖判讀** (`frontend/index.html`)
```
detectIntent() 
→ 判斷 'repair' vs 'shopping'
→ 路由到不同 API: /api/repair/chat 或 /api/chat
```

- **關鍵字**: `REPAIR_KEYWORDS` (水龍頭、漏水、維修等)
- **邏輯**: 純前端關鍵字匹配
- **鎖定機制**: 檢測到 repair 後會鎖定為 `repair` 模式

#### 2️⃣ **後端意圖判讀** (`backend/llm_service.py`)
```
_detect_conversation_intent()
→ 判斷 'company_info' | 'information' | 'product_search' | 'general'
→ 在 /api/chat 端點內部處理
```

- **優先順序**: 
  1. `company_info` (公司、品牌、電話等)
  2. `information` (資訊諮詢)
  3. `product_search` (商品搜尋)
- **邏輯**: 後端 LLM 或關鍵字判讀
- **沒有 'repair' 意圖判讀！** ❌

---

## ❌ 問題核心

### 問題 1: 前後端意圖層次不匹配

```
前端: repair | shopping
         ↓
後端: company_info | information | product_search | general
```

**衝突點**: 
- 前端把 `repair` 和 `shopping` 當作平行關係
- 後端在 `shopping` (也就是 `/api/chat`) 內部又細分為 `company_info` 和 `product_search`
- **後端完全沒有處理 `repair` 意圖** ❌

---

### 問題 2: 有對話歷史時的判讀失敗

**場景重現**:

```
步驟 1: 使用者: "你們公司賣什麼？"
→ 前端 detectIntent: shopping (沒有 repair 關鍵字)
→ 路由到 /api/chat
→ 後端 _detect_conversation_intent: "company_info"
→ ✅ 正確處理

步驟 2: 使用者: "水龍頭滴水怎麼辦？"
→ 前端 detectIntent: 
   - 檢查 intentModeLock
   - 如果前一次對話沒有鎖定，應該檢測到 'repair' ✅
   - 路由到 /api/repair/chat ✅
→ ✅ 應該能正確處理

步驟 3: 但實際測試失敗 ❌
```

### 問題 3: `routeMessageByIntent` 的歷史檢測 Bug

**位置**: `frontend/index.html` 行 1697-1710

```javascript
async function routeMessageByIntent(message, intent, options = {}) {
  // 🔄 檢測意圖切換
  let lastIntent = null;
  if (chatHistory.length > 0) {
    for (let i = chatHistory.length - 1; i >= 0; i--) {
      if (chatHistory[i].role === 'user') {
        lastIntent = detectIntent(chatHistory[i].content);  // ❌ Bug
        break;
      }
    }
  }
  
  const intentChanged = lastIntent && lastIntent !== intent;
  const payloadHistory = intentChanged ? [] : chatHistory.slice(-10);
  // ...
}
```

**問題分析**:
1. ❌ `detectIntent(chatHistory[i].content)` 使用**歷史訊息**重新檢測
2. ❌ 如果系統已鎖定 (intentModeLock = 'system')，會直接返回 `currentIntentMode`
3. ❌ 導致 `lastIntent` 總是等於當前鎖定的模式
4. ❌ `intentChanged` 永遠是 false，對話歷史不會被清空

**影響**:
- 當從 company_info 切換到 repair 時
- 前端檢測到 repair，路由到 /api/repair/chat
- 但對話歷史沒有清空，維修 API 收到了公司查詢的歷史 ❌
- 可能導致維修 API 混亂或誤判

## 🛠️ 修復方案

### 方案 A: 修復前端意圖切換邏輯（推薦）

#### 問題點 1: `detectIntent` 鎖定邏輯過於嚴格

**當前邏輯**:
```javascript
function detectIntent(message) {
  const manualLocked = intentModeLock === 'manual' && currentIntentMode !== 'auto';
  const systemLocked = intentModeLock === 'system' && currentIntentMode !== 'auto';
  if (manualLocked || systemLocked) {
    return currentIntentMode;  // ❌ 直接返回，不檢測新意圖
  }
  // ... 關鍵字檢測
}
```

**修復**: 允許系統鎖定時重新評估明確意圖

```javascript
function detectIntent(message) {
  const manualLocked = intentModeLock === 'manual' && currentIntentMode !== 'auto';
  if (manualLocked) {
    return currentIntentMode;  // ✅ 手動鎖定不可覆蓋
  }
  
  // 🆕 計算分數（無論是否鎖定）
  let repairScore = 0;
  let shoppingScore = 0;
  
  REPAIR_KEYWORDS.forEach(keyword => {
    if (message.includes(keyword)) repairScore++;
  });
  
  SHOPPING_KEYWORDS.forEach(keyword => {
    if (message.includes(keyword)) shoppingScore++;
  });
  
  // 🆕 判斷明確意圖
  let detectedIntent = 'shopping';
  if (repairScore > shoppingScore && repairScore > 0) {
    detectedIntent = 'repair';
  } else if (shoppingScore > repairScore && shoppingScore > 0) {
    detectedIntent = 'shopping';
  }
  
  console.log('🎯 [Intent] 意圖分析:', {
    message: message.substring(0, 50),
    repairScore,
    shoppingScore,
    detected: detectedIntent,
    current: currentIntentMode,
    lock: intentModeLock
  });
  
  // 🆕 系統鎖定時的強意圖切換
  if (intentModeLock === 'system' && currentIntentMode !== 'auto') {
    // 檢測明確的意圖切換（需要至少 1 個關鍵字）
    if (detectedIntent !== currentIntentMode && 
        ((detectedIntent === 'repair' && repairScore >= 1) ||
         (detectedIntent === 'shopping' && shoppingScore >= 1))) {
      console.log(`🔄 [Intent] 強意圖切換: ${currentIntentMode} → ${detectedIntent}`);
      setIntentMode(detectedIntent, 'strong-switch', 'system');
      return detectedIntent;
    }
    // 沒有明確切換，保持鎖定
    return currentIntentMode;
  }
  
  // 🆕 auto 模式首次檢測
  if (currentIntentMode === 'auto' && (repairScore > 0 || shoppingScore > 0)) {
    setIntentMode(detectedIntent, 'auto-detect', 'system');
  }
  
  return detectedIntent;
}
```

**改善點**:
- ✅ 系統鎖定不是絕對的，允許明確意圖切換
- ✅ 至少 1 個關鍵字就可以觸發切換（降低門檻）
- ✅ 保留手動鎖定的絕對優先權

#### 問題點 2: `routeMessageByIntent` 的歷史意圖檢測

**修復**: 建立純粹的意圖檢測函式

```javascript
// 🆕 新增：純粹的意圖檢測（不受鎖定狀態影響）
function detectIntentPure(message) {
  let repairScore = 0;
  let shoppingScore = 0;
  
  REPAIR_KEYWORDS.forEach(keyword => {
    if (message.includes(keyword)) repairScore++;
  });
  
  SHOPPING_KEYWORDS.forEach(keyword => {
    if (message.includes(keyword)) shoppingScore++;
  });
  
  if (repairScore > shoppingScore && repairScore > 0) {
    return 'repair';
  } else if (shoppingScore > repairScore && shoppingScore > 0) {
    return 'shopping';
  }
  return 'shopping';
}

async function routeMessageByIntent(message, intent, options = {}) {
  // 🆕 改進：使用純粹檢測
  let lastIntent = null;
  if (chatHistory.length > 0) {
    for (let i = chatHistory.length - 1; i >= 0; i--) {
      if (chatHistory[i].role === 'user') {
        lastIntent = detectIntentPure(chatHistory[i].content);  // ✅ 使用純粹檢測
        break;
      }
    }
  }
  
  const intentChanged = lastIntent && lastIntent !== intent;
  
  // 如果意圖切換，清空歷史避免干擾
  const payloadHistory = intentChanged ? [] : chatHistory.slice(-10);
  
  if (intentChanged) {
    console.log(`🔄 [Intent] 意圖切換: ${lastIntent} → ${intent}，清空對話歷史`);
  } else {
    console.log(`➡️ [Intent] 意圖延續: ${intent}，保留歷史 (${payloadHistory.length} 條)`);
  }
  
  // ... 其餘邏輯不變
}
```

**改善點**:
- ✅ `lastIntent` 基於實際訊息內容，不受鎖定狀態影響
- ✅ 正確檢測意圖切換
- ✅ 切換時清空歷史，避免污染

### 方案 B: 後端增加維修意圖判讀（備選）

如果不想修改前端，可以在後端 `/api/chat` 增加維修檢測並轉發：

```python
# backend/llm_service.py

REPAIR_KEYWORDS = [
    "水龍頭", "滴水", "漏水", "維修", "修理", "報修", 
    "故障", "壞掉", "不能用", "異常", "馬桶", "堵塞",
    # ... 其他維修關鍵字
]

def _detect_conversation_intent(query: str) -> str:
    """檢測對話意圖"""
    if not query:
        return "general"
    
    query_lower = query.lower()
    
    # 🆕 維修意圖檢測（最高優先級）
    repair_score = sum(1 for kw in REPAIR_KEYWORDS if kw in query)
    if repair_score >= 1:
        return "repair"  # 🆕 新增 repair 意圖
    
    # 公司資料查詢
    for category, patterns in COMPANY_INFO_PATTERNS.items():
        if any(pattern in query_lower for pattern in patterns):
            return "company_info"
    
    # ... 其他意圖檢測
```

```python
# backend/app.py - /api/chat 端點

@app.post("/api/chat")
async def chat_endpoint(req: ChatReq):
    # ... 前置處理
    
    # 🆕 檢測是否為維修意圖
    from llm_service import _detect_conversation_intent
    intent = _detect_conversation_intent(req.message)
    
    if intent == "repair":
        # 🆕 轉發到維修 API
        repair_req = RepairChatReq(
            message=req.message,
            history=req.history,
            session_id=req.session_id,
            topn=5
        )
        return await repair_chat_endpoint(repair_req)
    
    # 原有的 company_info / product_search 邏輯
    # ...
```

**優點**:
- 前端不需修改
- 後端統一管理所有意圖

**缺點**:
- 需要同步前後端的維修關鍵字
- 增加後端複雜度
- 可能影響效能（多一層判斷）

## ✅ 總結

### 問題根源
1. ❌ 前端鎖定邏輯過於嚴格，不允許系統鎖定時的意圖切換
2. ❌ 歷史意圖檢測使用了受鎖定狀態影響的函式
3. ❌ 意圖切換時對話歷史沒有正確清空

### 解決方案
1. ✅ 降低系統鎖定的門檻，允許明確意圖切換（至少 1 個關鍵字）
2. ✅ 建立純粹的意圖檢測函式，不受鎖定狀態影響
3. ✅ 正確檢測意圖切換並清空歷史

### 預期效果
- ✅ 公司查詢 ↔ 商品查詢 自由切換
- ✅ 公司查詢 ↔ 維修查詢 自由切換
- ✅ 商品查詢 ↔ 維修查詢 自由切換
- ✅ 對話歷史正確清理，避免污染
